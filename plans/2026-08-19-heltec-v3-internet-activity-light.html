MeshCore implementation plan · 19 August 2026

Put MeshCore inside the Internet.

A Heltec V3 repeater hidden in the sacred black box, with one external light that turns on for two seconds whenever the radio hears a packet.

Verdict: use an external LED on GPIO 7 and a small, opt-in firmware customization. The new lamp turns on for two seconds only when the radio receives a packet, never when this node sends. A later packet restarts the two-second timer.

01 / WHAT EXISTS

Most of the plumbing is already here.

The Heltec V3 pin map, an unused exposed GPIO, and a pre-parse receive callback are all present. The implementation adds a non-blocking external-light timer behind a dedicated build flag.

Available external output

GPIO 7 is exposed and unused

Heltec exposes GPIO 7 as J3 pin 18. MeshCore's V3 target does not assign it to the radio, OLED, battery monitor, GPS, or controls.

02 / CHOICE

Three ways to make it blink.

A separate lamp is the cleanest way to guarantee that visible activity means “heard,” not “sent.” GPIO 7 is the proposed default, but the build flag keeps it easy to change.

Option A · no code

Stock repeater

Use the onboard GPIO 35 LED, which indicates transmissions rather than received packets.

  • No firmware maintenance
  • Does not drive an external GPIO 7 LED
  • Does not meet the receive-only requirement

About 15 minutes, but wrong signal

Option B · dedicated target

Two-second external RX lamp

Add a small opt-in activity mode and a Heltec_v3_the_internet build environment, with the lamp on GPIO 7.

  • On for two seconds after every CRC-valid LoRa packet—not TX
  • Later packets restart the two-second countdown
  • No dummy packets and no network airtime cost

Roughly 1–2 hours including bench test

Option C · dual indication

Two external LEDs

Use separate GPIOs and colours for receive and transmit while leaving the onboard TX light hidden.

  • Packet meaning is completely unambiguous
  • More visually elaborate than the original prop
  • Adds a second output, resistor, and aperture

About 2–3 hours plus fabrication

03 / DESIGN

A dedicated lamp for receive.

The external activity controller alone owns GPIO 7. Stock transmit callbacks remain on the onboard GPIO 35 LED, so sending cannot start, extend, shorten, or cancel the visible external pulse.

TX does not enter this path.

Only logRxRaw() can extend the GPIO 7 lamp deadline. It is never called from logTx(), onBeforeTransmit(), or onAfterTransmit().

04 / IMPLEMENT

A deliberately small change.

Keep the default repeater untouched. The behaviour exists only when activity-light build flags are present, so other boards and release targets retain their current semantics.

Add an opt-in Heltec build environmentCreate Heltec_v3_the_internet beside the existing repeater target.
  • Reuse the Heltec V3 radio, display, and simple-repeater source filters.
  • Set the default advert name to "The Internet".
  • Leave P_LORA_TX_LED=35 unchanged for the onboard TX indicator. Define the separate external output as ACTIVITY_LED_PIN=7 with ACTIVITY_LED_ON_MILLIS=2000.
  • Keep timing values compile-time constants; no new persisted preferences or CLI surface are needed for a joke prop.

  -D ACTIVITY_LED_ON_MILLIS=2000

Add non-blocking activity timing to the repeaterGuard every addition with ACTIVITY_LED_PIN.
  • Store a single LED-off deadline on MyMesh.
  • Initialise GPIO 7 low during repeater startup.
  • Service the light once per main loop; never call delay().
  • Use wrap-safe unsigned time comparisons and extend—not replace—the current deadline when events overlap.
  • Expose one focused loopActivityLed() method if needed; avoid a generic indicator framework.
Trigger the pulse at the right receive boundaryUse the existing logRxRaw() override.
  • Start the two-second pulse before the existing MESH_PACKET_LOGGING conditional.
  • This represents “heard a packet” as a complete LoRa frame that passed the radio's read/CRC checks.
  • Do not use onRecvPacket(): flood-score scheduling may delay that callback, and it excludes frames that fail MeshCore parsing.
  • Do not add any pulse call to logTx() or the board's transmit hooks. A local send must not illuminate the external LED.
  • Corrupt/noise events remain unlit by design. Showing all channel energy would require a different lower-level RSSI/CAD feature and is outside this joke.
Build, flash, and configureProduce a normal ESP32-S3 binary and set legal regional radio parameters. 
pio run -e Heltec_v3_the_internet
pio run -t upload -e Heltec_v3_the_internet
  • On first boot, use the MeshCore console/configurator to select the correct legal frequency preset and change the default admin password.
  • Leave power saving off so the main loop services the two-second deadline promptly.
  • The repeater can still participate normally in MeshCore; the receive light is purely local.

05 / VERIFY

Bench checks with visible outcomes.

This is hardware-timing behaviour, so a focused build check plus a short two-radio bench test is more valuable than a large unit-test scaffold.

✓

Target builds cleanly

pio run -e Heltec_v3_the_internet succeeds without changing the stock Heltec_v3_repeater output.

✓

Two-second deadline

After a single received frame, GPIO 7 stays high for 2.0 s ± one normal loop iteration, then returns low.

✓

Every accepted frame pulses

Send direct, flood, and duplicate packets from a second node; each radio receipt produces an immediate visible pulse.

✓

Local TX does not pulse

Trigger a self-advertisement with no incoming traffic; the external GPIO 7 LED remains dark throughout the transmission.

✓

Traffic still flows

Confirm the device advertises, receives, and forwards as a repeater while the light is active.

✓

Retrigger is stable

A packet arriving while the lamp is on restarts the deadline, keeping it lit until two seconds after the newest packet.

✓

No delay-based stalls

Dense packet traffic does not block the mesh loop, serial console, display refresh, or watchdog servicing.

06 / PRACTICAL

Firmware is the easy bit.

The enclosure and radio placement will decide whether the result feels like a prop or a small electronics project trapped in a box.

LED ownership
Keep the external activity lamp on GPIO 7. GPIO 35 remains the onboard TX light; the two paths must not be aliased to the same pin.
Power saving
Light/deep sleep can stretch local timer behaviour. For a USB-powered desk prop, keep power saving disabled.
Busy mesh
In a dense area the lamp may look almost solid. If that happens, shorten RX pulses or add a short minimum-dark interval after bench testing.
Regional settings
A repeater is a real transmitter. Configure the legal frequency/preset and avoid unnecessary TX power indoors.

Prop checklist

  • Wire GPIO 7 → 330 Ω resistor → LED anode, then LED cathode → GND. GPIO 7 is J3 pin 18 on the Heltec V3 header.
  • Use a diffused red LED and mount it directly behind a drilled aperture or translucent insert; do not drive an LED directly without a series resistor.
  • Keep the antenna outside the box, or build the shell from RF-transparent plastic; do not bury it behind metal foil or a battery.
  • Leave access to USB-C, reset/boot controls, and enough ventilation for continuous powered use.
  • Add strain relief so lifting “the Internet” by its cable does not tear the Heltec connector off the board.
  • If the LED is too dim, reduce the resistor toward 220 Ω within the LED's rating; do not make firmware pulses excessively long.

Recommended next move

Build the dedicated Heltec_v3_the_internet target, wire a diffused external LED to GPIO 7 through 330 Ω, and trigger it only from logRxRaw(). Each accepted radio packet turns it on for two seconds; no traffic means no light.
